# 什么是沙箱:概念与三种实现方式

沙箱不是一个具体的技术名词，而是一类手段的总称。无论是在操作系统里隔离进程、在浏览器里限制网页脚本、在云计算里租户之间做资源隔离，还是给 AI Agent 的执行能力加一道边界，沙箱解决的都是同一个问题：让一段代码或一个程序在受限的范围内运行，使它无法破坏或触及范围之外的东西。

回到 AI Agent 这个场景，沙箱的实现方式同样可以按约束施加的位置分成三种。下面逐一看它们各自怎么工作、各自适合什么场景，最后再用 DeepSeek Harness 的代码把前两种方式落一遍。

## 第一种方式：在工具层自检

Agent 框架通常会给 Agent 提供一组"工具"——这些工具是框架内的函数，Agent 通过调用它们来操作外部世界。走这条路径的每一次操作，在真正执行之前，框架都可以拦截并判断：这个操作，在当前策略下是否被允许。

检查的粒度取决于工具本身的设计。一个文件写入工具可以在写入前解析目标路径，判断它是否落在允许的目录内；一个网络请求工具可以检查目标域名是否在允许列表里；一个数据库工具可以限制允许执行的 SQL 操作类型。关键在于，因为执行操作的是框架自己的代码，框架有能力在操作发生之前把它拦下来。

这种方式的边界也很清楚：它只约束"走工具通道"的操作。如果框架内另有代码绕开工具直接执行操作，或者 Agent 通过其他路径（比如自己启动一个外部进程）来达到目的，这层检查是管不到的。它约束的是工具的输入，不是整个运行环境。

## 第二种方式：把规则交给操作系统

Agent 很多时候不是通过工具来操作，而是直接执行一条命令——启动一个真实的、独立的外部进程。这个进程可以是 shell 脚本、编译好的二进制、或者任何能在系统上运行的东西。框架既无法控制这个进程内部的每一步行为，也无法在它每一次写文件、发网络请求时插一脚。

外部进程的不可信是根本性的：它可以派生子进程，可以直接调底层系统调用，任何在框架代码里做的前置检查都存在绕过去的路径。所以对这种情况，约束必须放在一个外部进程够不着、也关不掉的地方——操作系统。

要让操作系统去拦，框架得先"告诉"它规则是什么。这一步需要借助一个外部的启动器：把策略翻译成操作系统能执行的限制（哪些路径可写、哪些系统调用可用、哪些网络地址可达），在这个限制下启动命令。不同的平台有不同的实现：Linux 上有 bwrap 和 Landlock，macOS 上有 sandbox-exec，Windows 上有受限令牌和 ACL。这些启动器的共同点是，它们把一套规则安装到内核，命令及其所有派生进程都在内核的监管下执行，任何越界操作都会被内核直接拒绝，而不是被框架代码判断。

还要保证一个前提：如果当前机器上没有一个可用的启动器，框架宁可拒绝执行，也不能把命令裸放出去。约束可以失败，但不可以被静默绕过。

因为拦截发生在内核一侧，命令被拒绝之后的表现也需要单独判断：它是被规则拦住了，还是命令自己执行失败了，还是启动器本身出了问题。这三者的处置逻辑完全不同，分类错误会让后续行为偏离预期。

## 第三种方式：完全隔离的执行环境

前面两种方式有一个共同的前提：Agent 仍然运行在宿主系统上，共享同一个内核和文件系统。约束的对象是"操作"，而不是"环境"。当约束的粒度需要覆盖得更深——比如不仅要限制 Agent 写什么，还要限制它读什么，或者限制它访问任何宿主的计算资源——那就需要把整个执行环境替换掉。

这种方式下，Agent 看到的是一个独立的环境：容器、微虚拟机、或者远程沙箱。它在这个环境里执行的所有操作，都只作用于环境内部的文件系统、网络栈和进程空间，与宿主物理隔离。宿主只暴露有限的、受控的接口给这个环境，其余的一切对 Agent 都是不可见的。

代价也随之而来：Agent 不再直接操作宿主真实文件，你失去"它改的就是你磁盘上那个文件"的实时性；环境的创建和销毁也有开销，不像前两种方式那样几乎零成本。什么场景选哪一层，取决于你需要隔离到什么程度。

## 一个统一的视角

把三种方式并排看，差别不在最终效果，而在约束施加在哪一层。

- 工具层自检：约束在框架代码里，靠执行前拦截。
- 交给操作系统：约束在内核里，靠外部启动器安装规则。
- 完全隔离：约束在环境本身，靠不共享宿主资源。

为什么刚好这样分布？因为约束要放在"执行者够不着的地方"。第一种方式的执行者是框架自己的代码，代码里就能拦；第二种方式的执行者是外部进程，只能让内核拦；第三种方式要约束整个执行体，就只能换环境。这条线是看任何 Agent 沙箱时最值得抓的视角。

## 以 DeepSeek Harness 为例

DeepSeek Harness 同时使用了前两种方式，在同一个宿主文件系统上落地。

它把约束的规则统一放在一个策略中心里。每一次工具调用或命令执行前，策略中心回答两个问题：当前用什么模式、工作区根在哪。模式有三种：只读、工作区可写、完全放开。解析的优先级固定：显式获批的模式，高于会话最近一次切换，再高于部署默认值；工作区根取会话创建时的目录。会话切换被记成日志里的一条事件，重放就能恢复，多会话互不干扰。

### 工具层自检：文件工具

Harness 的文件工具在真正写入前，先过一次检查。按当前策略取到模式，只读就直接拒绝；工作区可写就重新解析目标路径——把符号链接和上级目录全部展平，得到磁盘上的真实位置——再判断它是否落在允许写入的目录集合内。注意它返回的是重新解析过的路径，而不是模型给的原字符串，所以"检查的是谁，写的就是谁"，不给检查之后路径被换掉留窗口。

```ts
// 核心判断：先验真实路径，再判是否落在可写根内
const policy = sandboxPolicy.resolve()
const fresh = await resolve(target)                       // 重新解析成真实路径
if (mode === 'read-only') throw deny('file access denied under read-only mode')
if (mode === 'workspace-write' && !underAny(fresh, writableRoots(policy)))
  throw deny('file access denied under workspace-write mode')
return fresh                                              // 用验证过的这个目标去写
```

### 交给操作系统：bash 命令

当 Agent 需要执行一条系统命令时，Harness 的处理流程和文件工具完全不同。它不会直接跑 `bash -c "..."`，而是把这条命令交给沙箱服务，由后者决定"用什么启动器、带什么限制参数"来包装它，最后返回一个可以直接 spawn 的完整命令。

这个包装过程分成三步。第一步，Harness 根据当前会话的策略，算出"哪些路径可写"——这个规则和文件工具用的是同一份，定义只有一处：

```ts
function writableRoots(policy) {
  if (policy.mode !== 'workspace-write') return []
  return [...new Set([policy.workspaceRoot, '/tmp', tmpdir()].map(canonicalPath))]
}
```

第二步，把这份可写路径集合翻译成当前平台启动器能理解的参数。不同平台有各自的启动器，但翻译逻辑是写死的——输入是策略，输出是参数列表，中间没有任何模型或外部输入参与。以 Linux 上的 bwrap 为例：

```ts
function bwrapProfileArgs(policy) {
  const args = ['--ro-bind', '/', '/', '--dev', '/dev', '--unshare-pid', '--proc', '/proc']
  if (policy.mode === 'workspace-write') args.push('--tmpfs', '/tmp', '--bind', root, root)
  return args
}
```

bwrap 的思路是把整个宿主根目录以只读方式挂载给命令，工作区可写时再单独挂一个可写的 `/tmp` 和工作区目录。macOS 上 seatbelt 的做法不同——它用"默认拒绝所有写、白名单放开这些目录"的 SBPL 配置——但翻译函数的输入和输出结构是一样的：策略进，参数出。

第三步，沙箱服务把启动器路径、平台参数、以及原命令拼成一条完整的调用。核心逻辑是 `confine()` 方法：它先根据平台选择启动器（Linux 上优先 bwrap，不可用则退到 Landlock；macOS 用 seatbelt；Windows 用 ACL 受限令牌），用上面第二步的函数生成平台参数，最后把启动器、参数、分隔符 `--`、以及原命令拼在一起返回。原命令在 `--` 后面一字不改，真正的限制全在 `--` 前面的参数里。

```ts
const confined = sandbox.confine(['bash', '-c', command], policy)
// confined.argv 等价于 ['bwrap', '--ro-bind', '/', '/', ..., '--', 'bash', '-c', command]
const result = await runArgv(confined.argv)
```

启动器拿到这个包装后的命令，先按参数把限制装到内核——bwrap 创建隔离的挂载命名空间，Landlock 安装内核规则集，seatbelt 应用 SBPL 配置——然后 `exec` 原命令。此后原命令及其所有派生进程的每一次写操作，都要经过内核按规则逐条比对，越界即被拒绝。整个过程里，原命令感知不到这些限制的存在，也关不掉它。

还要保证一个前提：如果当前机器上没有任何可用的启动器，`confine()` 会直接拒绝，不返回任何可执行的命令。约束可以失败，但不可以被静默跳过。

命令执行完后，Harness 还需要从它的输出里分辨三类情况：命令自己执行失败了、被规则拦住了、还是启动器本身出了问题。启动器的返回结果里携带了它自己的拒绝特征（比如 bwrap 的 "read-only file system"、Landlock 的 "permission denied"），Harness 拿这些特征去匹配命令的输出，判断属于哪种情况。三类情况的处置逻辑完全不同，分类错误会让后续行为偏离预期。

### 完全隔离环境

第三种方式在 Harness 里是独立的实验方向，把文件与进程两个底层能力整体指向一个 E2B 微虚拟机。它不属于前两种方式的"同宿主"约束，而是用于需要整体隔离时的并行路线。

## 总结

一个 Agent 的能力越强，约束它就越不是在"限制它"，而是在"保证它能被安全地使用"。三种隔离方式回答了同样的问题——怎么让 Agent 保留操作能力，同时把破坏半径收窄——只是各自把约束放在不同的位置。DeepSeek Harness 的选择是前两种：用同一套规定，在工具层和操作系统层各自落地，在宿主文件系统里既把破坏范围收紧到工作区，又让 Agent 继续直接改真实文件。约束在它够得着的地方执行，而不是靠它自觉。
